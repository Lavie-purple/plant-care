# 断言强度验证记录

本文件记录 `AGENTS.md` 要求的「每写完一条断言，先用能骗过它的坏法真注入一次」的验证结果。

原则：**不会变红的断言直接删。**

## 已删除的无效断言

开发过程中有两条断言经变异检测判定为**无效**，已按规则删除或重写。记录在此以免重犯。

### 1. 「守卫逻辑自检」（已删除）

原写法是在测试里复制一遍 `finish()` 的守卫代码，然后断言它能拦住空 `sourceId`。

**为什么无效**：变异测试删掉引擎里真正的守卫后，这条测试依然全绿。原因是测试只验证了它自己复制的那份副本，与引擎实现毫无关系。

**根因**：`?? plant.id` 兜底让 `sourceId` 永远非空，所以「检查非空」这个守卫本身在当前实现下是死代码。

### 2. 「sourceId 必须在输入集合里」（已重写）

原写法构造 `validIds = {plant.id, rule.id, watering.id, weather.id}`，断言每条依据的 `sourceId` 都在其中。

**为什么无效**：注入 `sourceId: 'unrelated-entity'` 后测试全绿。

**根因**：注入点选在「降雨缓解」依据上，而当时的测试场景是**室内靠窗 + 降雨概率 70%**。室内 `rainFactor = 0.15`，有效降雨概率 `70 × 0.15 = 10.5` 低于阈值 40，**降雨缓解分支根本没被触发**，注入的坏代码落在死路径上。

**教训**：变异必须打在**测试确实会触发的路径**上，否则验证的是一条不存在的代码路径，等于没验证。

**重写后**：改用「露台 + 降雨概率 80%」场景，该场景确定会触发降雨缓解分支，再断言依据的 `sourceId` 指向天气快照。重新注入后测试变红，验证通过。

## 引擎判定链条的语义（供后续改动参考）

改动判定逻辑前先理解这四档的含义，它们不是随意命名的：

```
NO_ACTION   未到最短周期，不建议浇水
CHECK       已进入推荐周期，先看盆土。浇水不算错，但谈不上该浇
WATER_NOW   超出推荐周期上限，该动手
DELAY       超出推荐周期上限，但植物受雨影响、近期有雨，等 1-2 天
```

**曾经的设计错误**（已被测试抓住）：把降雨延期做成了「拉长周期上限」（`adjustedMax = max + rainRelief`）。这会导致 11 天未浇、明天下雨的植物落到 `CHECK`，而用户的真实问题是「今天浇还是明天浇」，答案应该是 `DELAY 1 天`。修正后判定改为「先看是否到达周期上限，超了才在 WATER_NOW / DELAY 之间二选一」。

第 5 条最初是无效断言（只断言 `name` 字段不存在，注入 `data` 字段照样通过），
已改为严格断言载荷的键集合恰好是三个。

### 存储层开发中发现的三个问题

1. **`plantEvents` 缺 `by_plant` 索引**。`growthTimeline()` 和 `plantEvents()` 都按该索引查询，
   但 SCHEMA 里只定义了 `by_plant_date` 和 `by_plant_type`。写入成功、查询报
   "object store did not exist"——错误信息完全指错方向。修复时把 `DB_VERSION` 从 1 提到 2，
   否则老库不会重建索引。
2. **测试耗时 120 秒**。根因是 Repository 的数据库连接未关闭，悬挂的连接阻塞后续
   `open()` 阻塞在 `onupgradeneeded`。加 `afterEach` 统一关闭后降到 385 毫秒。
3. **`saveWeatherSnapshot` 是 O(n²)**。每次保存都 `getAll` + 全表排序，存 200 条要扫 200 次。
   按 AGENTS.md「禁止 O(n²)」改为先 `count`，不超量直接返回（O(1)）。

### 演示脚本抓出的真 bug

`scripts/demo-loop.mjs` 打印真实输出时发现：`loadWeather()` 在 Provider 失败后
回落到 `latestWeatherSnapshot()` 并当作可用数据返回。用户断网后会拿到几分钟前的

修复：fetch 失败一律返回 `unavailable`，缓存改由界面层显式调用 `readCachedWeather()`
展示，且必须带 `lastSuccessAt` 让用户知道数据有多旧。

**这个 bug 是靠「把真实输出打印给人看」发现的，任何绿测都测不出来。**

### 浏览器实测抓到的三个 bug（任何绿测都测不出来）

这三个是靠「打开浏览器看真实输出 + 截图核对」发现的，`AGENTS.md` 要求的
「上线 = 部署 + 访客视角首屏核对」不是形式主义：

1. **新植物被误判为「无需处理」**。引擎把「没有浇水记录」和「0 天前浇过」
   当成同一件事（`daysSince ?? 0`），导致首屏显示「今天 0 盆要处理」。
   这与痛点第一条「记不住上次什么时候浇水」直接矛盾。
   修复后：无记录 → CHECK，并明确标注 `source: unknown`（是事实缺失，不是推断）。

2. **来源显示为 `来源：plant-3`**。可追溯性对机器成立，对人不成立。
   新增 `describeSource()` 把 id 翻译成「浇水记录 09-21 14:20 · 实测」，
   并只给真正有原始记录可核对的来源（浇水记录、天气）加「可点开核对」入口，
   推断与未知不给假入口。

3. **5K 屏上行长超过 150 字符**。5K + 100% 缩放下内容拉满宽度，
   正是 AGENTS.md 禁止的「信息密度过高的后台」观感。
   增加 `max-width: 720px / 860px` 限宽。

另外两个布局 bug 也是截图发现的：底栏 fixed 压住主导航、
导航 max-width 约束导致四个按钮文字挤成一团。

### 我自己写错又改对的两个测试

- 「同一次观测的两次抓取必须有不同 id」——**方向就错了**。
  正确语义是 snapshot 的身份是「这份天气数据」，同一次观测重复抓取
  应当是同一条记录并覆盖，否则缓存会堆积重复天气。
- 「无记录时 source 应为 measured」——**前提错了**。
  无记录是事实缺失，必须是 `unknown`，不能伪装成实测。

| 注入的坏法 | 结果 | 保护的规则 |
|---|---|---|
| 补录时把未填的水量标成 user_stated | 1 个测试变红 | D-13：未填不得伪装成用户手填 |
| 补录时用估算值覆盖已有估算 | 1 个测试变红 | 同上，保持估算来源不变 |
| 悬挂引用（浇水记录引用不存在的植物） | 1 个测试变红 | 导入必须整体拒绝 |
| 版本不匹配仍放行导入 | 1 个测试变红 | 不做猜测迁移 |

| 校验失败仍写入一半 | 1 个测试变红 | 绝不允许半截数据集 |

### 这批最要紧的两个设计决定

**1. 队列必须有终点。** 批量浇水是效率最高的功能，但要求当场填 N 份表单不可接受，
所以剩余字段进队列。可没有终点的队列会变成没人敢打开的垃圾场。
因此 `completionState` 增加 `expired` 态：超过 14 天未补全自动降级为「历史空白」，
水量记为未知、不再提示。**数据仍在，只是统计不含它**——这是主动放弃，不是数据丢失。
收敛不变量已写成测试：40 天里每天产生 3 条待补全且用户从不补，队列必须收敛。

**2. 导入必须先校验、让你确认、再写入。** 分成 readImport 与 commitImport 两步，
中间必须有人看一眼。任何一条记录不合法就整体拒绝——
「导进去一半」比「导不进去」危险得多。

### 顺带修的两个 schema 漏项

- `PendingRuleConflict` 缺 `version`，导致无法走乐观锁。建 schema 时漏了。
- `DataTransferService` 一度直接访问 `service.repo` 私有字段，
  改为在 service 上提供 `dataTransfer()` 访问器，界面层不接触 Repository。

| 注入的坏法 | 结果 | 保护的规则 |
|---|---|---|
| 缺图仍放行导入 | 1 个测试变红 | **D-18：只导出引用等于假装备份过** |

| 同内容存两份 | 已由哈希去重保证 | 连点两次同一张图不占两份空间 |

### 这个缺口是怎么被发现的

写导出功能时我做了往返测试，用的是 `images: ['img-1']` 这样的假 id，
而库里根本没有对应图片记录。**旧版代码会静默接受这份数据**，
用户导进去之后界面上是一堆指向不存在图片的记录，看起来像碎图，
而且他根本不知道丢了什么。

现在引用完整性检查会拦下来，并明确告诉他「有 1 张照片找不到」。
这也是为什么我把测试数据改成了真存一张图片：往返链路必须真的跑通，
而不是靠一个恰好能过的假数据。

### 压缩的三条降级路径

1. 小图不压（低于 200KB），避免二次劣化
2. WebP 不支持则回退 JPEG
3. 编码彻底失败或压完更大，则原样保留并记录 warning

任何一条路径都不丢图。这是上传功能的基本要求。

| 注入的坏法 | 结果 | 保护的规则 |
|---|---|---|
| 名字为空仍写库 | 1 个测试变红 | 校验必须在提交前拦住 |

### 浏览器实测抓到的两个真 bug

**1. 示例数据会覆盖用户数据。**
`main.tsx` 里有「库为空就播两盆示例植物」的逻辑。开发时它掩盖过真实问题；
更严重的是在库还没加载完的瞬间，那个「空」判断会误判成真的空库。
已删除全部示例数据——示例数据属于测试夹具（`tests/` 里已有），不属于生产代码。

**2. `open()` 挂起 = 纯黑屏。**
建表阶段一旦出错，`onsuccess` 和 `onerror` 都不触发，`open()` 永远挂起，
页面表现为一片黑屏，用户看不到任何信息也拿不到错误。
这轮加了四路守卫：成功 / 建表出错 / 明确报错 / 10 秒超时，
并且 `main.tsx` 把失败渲染成人能读的说明 + 技术细节。

触发它的场景很真实：另一个标签页开着连接时执行 `deleteDatabase`，
删除被阻塞，之后所有 `open()` 排队等待。实测确认超时信息正确显示。

## 规则冲突确认（第十批）

| 注入的坏法 | 结果 | 保护的规则 |

### 间歇性失败暴露的真 bug

天气快照 id 曾经是 `om-${observedMs}-${now}-${lat}`，抓取时刻参与 id。
这导致**同一次观测的重复抓取产生不同 id**，缓存会堆积重复天气。
它表现为一个偶发失败（两次抓取差 1 毫秒），连跑几次才复现一次。
修正为 `om-${observedMs}-${lat}-${lon}` 后连跑 5 次稳定全绿。

**教训：间歇性失败不要当成测试不稳定。** 它通常是真 bug 的表征。

### 错误信息的两层结构

天气失败的 `message` 现在是人话（「无法连接到天气服务」），
完整 URL 和原始错误移到 `serverResponse`。
截图里那一行从占两行变成占一行。之前把几百字符的查询串直接甩给用户，
既看不懂又挤占界面；远程诊断需要的细节一条没少。

| 把天气接口改成 cache-first | 1 个测试变红 | **天气永不缓存**：断网时会拿旧天气算浇水建议，用户以为那是现在的 |
| 把跨域第三方也缓存 | 1 个测试变红 | 第三方资源不该进本应用的缓存 |

### 开发中发现的两个真问题

**1. 跨域判断的注释与实现不符。**
注释写着「跨域请求一律不碰」，实现却只拦了黑名单里的两个天气主机——
任何第三方 CDN 都会被写进本应用的缓存，制造无法预测的失效顺序。
现已改为按 origin 判定，注释与实现一致。

**2. 顶层 await 导致生产构建失败。**
`main.tsx` 用了顶层 `await repo.open()`，而 Vite 默认构建目标
（chrome87 / edge88 / firefox78 / safari14）不支持，
**生产构建直接报 fatal，压根发不出去**。改为 `.then()` 链后构建通过。

### 离线验证是真做的，不是推断的

1. 生产构建，334KB（gzip 102KB）
2. 起 preview 服务器，SW 注册成功、activated、controller 已接管
3. 缓存里确认 6 个外壳资源（`/`、manifest、两个图标、CSS、JS）
4. **`taskkill` 停掉服务器**（curl 确认 HTTP 000 完全不可达）
5. 刷新页面 → 照常打开，界面正常，天气明确显示不可用

第 4、5 步是这套验证的关键：不停服务器，「能打开」证明不了任何事。

## WebP 静默失效与移动端导出（第十三批）

| 注入的坏法 | 结果 | 保护的规则 |
|---|---|---|
| 编码器返回类型不符仍当成功 | 1 个测试变红 | **Safari 的 toBlob('webp') 安静返回 png，不抛异常** |
| 两种格式都失败却仍标成 jpg | 1 个测试变红 | 宁可保留原图，不存类型不符的假货 |
| ZIP 条目数超上限静默截断 | 1 个测试变红 | 静默截断比抛错危险 |
| ZIP 解析到坏数据 | 1 个测试变红 | 必须报明确错误 |

### WebP 那个 bug 的性质

`canvas.toBlob('image/webp')` 在 Safari 上**不抛异常**，它安静地返回一个
`type` 为 `image/png` 的 Blob。原来的实现只靠 `try/catch` 判断是否支持，
所以**回退逻辑在 Safari 上从来没生效过**——存下的是「后缀 .webp、
内容 PNG」的假货，导出时的格式判断会跟着一起错。

现在改为校验返回 Blob 的实际 `type`，不匹配就当失败处理。
另外补了一条：两种格式都拿不到时保留原图，而不是留一个类型不符的东西。

### 移动端导出（真实的可用性问题）

File System Access API 的选目录在**移动端全部不可用**
（iOS Safari、Android Chrome 都没有）。原降级路径只下载 JSON，
照片全丢——**用户在手机上拍的照片根本拿不出来**。

改为打包成 ZIP：`data.json` + `images/` 一起下载，电脑上解压即可。
自己实现了 store 模式的 ZIP 打包器（含 CRC32），15 个测试覆盖，
含标准向量 `crc32("123456789") = 0xcbf43926`。

不用 deflate 是刻意取舍：图片本身已压缩，再压几乎不省空间，
却要付出 CPU 与内存。

## 部署配置（第十四批）

校验脚本 `scripts/verify-build.mjs` 本身的断言强度也做了变异检测。
第一版有三条是假断言，被注入后仍全绿：

| 注入的坏法 | 第一版 | 修正后 |
|---|---|---|
| 从不缓存名单里删掉天气接口 | 漏过 | 变红 |
| manifest 图标路径改回绝对路径 | 变红 | 变红 |
| 删掉 404.html | **漏过** | 变红 |
| index.html 资源路径改回根路径 | 变红 | 变红 |

**两条假断言的根因：**

1. `sw.includes('api.open-meteo.com')` —— `api.open-meteo.com` 是
   `geocoding-api.open-meteo.com` 的**子串**。把天气接口从名单里删掉，
   地理编码接口还在，`includes` 照样返回 true。
   改为逐项精确匹配后抓住。

2. `readFileSync(404.html)` —— 文件不存在时直接抛异常中断脚本，
   退出码非零但看不出是哪一项坏了。**校验脚本自己崩掉比校验失败更难查。**
   改为先 `existsSync` 判断，把缺失记成一条明确的 FAIL。

### base 路径三处一致

`vite.config.ts`、`scripts/postbuild.mjs`、`scripts/verify-build.mjs`
必须算出同一个 base。任何一处分歧都会让 SW 缓存路径与实际资源路径错开，
离线能力静默失效。三处共用 `scripts/base-path.mjs` 的 `resolveBase`。

其中还拦掉一个 Windows 坑：Git Bash 会把命令行里的 `/xxx/`
转成 `D:/.../xxx/`。`resolveBase` 检测到盘符会直接报错并说明原因。
