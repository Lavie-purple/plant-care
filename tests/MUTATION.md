# 断言强度验证记录

本文件记录 `AGENTS.md` 要求的「每写完一条断言，先用能骗过它的坏法真注入一次」的验证结果。

原则：**不会变红的断言直接删。**

---

## 验证有效的断言

| 注入的坏法 | 结果 | 保护的规则 |
|---|---|---|
| 把 `recordDate` 改成忽略 `date` 字段，所有历史都当成「今天」 | 30 个测试变红 | `daysSince` 计算正确性 |
| 湿度 ≥ 75% 时也设 `rainReliefDays`（潮湿即延期） | 4 个测试变红 | 延期只由降雨驱动，湿度仅作佐证 |

## 已删除的无效断言

开发过程中有两条断言经变异检测判定为**无效**，已按规则删除或重写。记录在此以免重犯。

### 1. 「守卫逻辑自检」（已删除）

原写法是在测试里复制一遍 `finish()` 的守卫代码，然后断言它能拦住空 `sourceId`。

**为什么无效**：变异测试删掉引擎里真正的守卫后，这条测试依然全绿。原因是测试只验证了它自己复制的那份副本，与引擎实现毫无关系。

**根因**：`?? plant.id` 兜底让 `sourceId` 永远非空，所以「检查非空」这个守卫本身在当前实现下是死代码。

### 2. 「sourceId 必须在输入集合里」（已重写）

原写法构造 `validIds = {plant.id, rule.id, watering.id, weather.id}`，断言每条依据的 `sourceId` 都在其中。

**为什么无效**：注入 `sourceId: 'unrelated-entity'` 后测试全绿。

**根因**：注入点选在「降雨缓解」依据上，而当时的测试场景是**室内靠窗 + 降雨概率 70%**。室内 `rainFactor = 0.15`，有效降雨概率 `70 × 0.15 = 10.5` 低于阈值 40，**降雨缓解分支根本没被触发**，注入的坏代码落在死路径上。

**教训**：变异必须打在**测试确实会触发的路径**上，否则验证的是一条不存在的代码路径，等于没验证。

**重写后**：改用「露台 + 降雨概率 80%」场景，该场景确定会触发降雨缓解分支，再断言依据的 `sourceId` 指向天气快照。重新注入后测试变红，验证通过。

## 引擎判定链条的语义（供后续改动参考）

改动判定逻辑前先理解这四档的含义，它们不是随意命名的：

```
NO_ACTION   未到最短周期，不建议浇水
CHECK       已进入推荐周期，先看盆土。浇水不算错，但谈不上该浇
WATER_NOW   超出推荐周期上限，该动手
DELAY       超出推荐周期上限，但植物受雨影响、近期有雨，等 1-2 天
```

**曾经的设计错误**（已被测试抓住）：把降雨延期做成了「拉长周期上限」（`adjustedMax = max + rainRelief`）。这会导致 11 天未浇、明天下雨的植物落到 `CHECK`，而用户的真实问题是「今天浇还是明天浇」，答案应该是 `DELAY 1 天`。修正后判定改为「先看是否到达周期上限，超了才在 WATER_NOW / DELAY 之间二选一」。

## 天气数据源（第二批）

| 注入的坏法 | 结果 | 保护的规则 |
|---|---|---|
| 去掉 km/h → m/s 换算 | 2 个测试变红 | 单位换算：大风阈值按 m/s 算，换错会让 8.9 km/h 被当成 8.9 m/s |
| 去掉秒 → 小时换算 | 1 个测试变红 | `sunshine_duration` 单位是秒 |
| 非 2xx 不抛错（吞掉） | 1 个测试变红 | 服务端原文必须回显，便于远程诊断 |
| 未知天气码编造成「多云」 | 1 个测试变红 | 未知码原样显示，不得编造描述 |

**这两个单位换算是真实踩到的坑**：写代码前先用 curl 拉了接口实际响应，
发现 `wind_speed_10m` 是 km/h 而引擎阈值按 m/s 设，`sunshine_duration` 是秒而非小时。
若凭记忆写，这两处会让高温和大风规则静默失效。

## 存储层（第三批）

| 注入的坏法 | 结果 | 保护的规则 |
|---|---|---|
| 乐观锁失效（`if (false)`，无条件覆盖） | 3 个测试变红 | **D-17：后提交者必须被拒，不得静默覆盖** |
| 成长时间线不过滤类型 | 1 个测试变红 | D-08：时间线是 PlantEvent 的视图，不是全量 |
| 浇水历史不按日期倒序 | 1 个测试变红 | 倒序是「最近一次浇水」的正确性前提 |
| 天气快照不裁剪 | 1 个测试变红 | 防止存储无限增长 |
| 广播载荷塞入完整实体 | 1 个测试变红 | 广播只带 kind/store/id，图片无法序列化，接收方必须自己重读 |

第 5 条最初是无效断言（只断言 `name` 字段不存在，注入 `data` 字段照样通过），
已改为严格断言载荷的键集合恰好是三个。

### 存储层开发中发现的三个问题

1. **`plantEvents` 缺 `by_plant` 索引**。`growthTimeline()` 和 `plantEvents()` 都按该索引查询，
   但 SCHEMA 里只定义了 `by_plant_date` 和 `by_plant_type`。写入成功、查询报
   "object store did not exist"——错误信息完全指错方向。修复时把 `DB_VERSION` 从 1 提到 2，
   否则老库不会重建索引。
2. **测试耗时 120 秒**。根因是 Repository 的数据库连接未关闭，悬挂的连接阻塞后续
   `open()` 阻塞在 `onupgradeneeded`。加 `afterEach` 统一关闭后降到 385 毫秒。
3. **`saveWeatherSnapshot` 是 O(n²)**。每次保存都 `getAll` + 全表排序，存 200 条要扫 200 次。
   按 AGENTS.md「禁止 O(n²)」改为先 `count`，不超量直接返回（O(1)）。

| 注入的坏法 | 结果 | 保护的规则 |

### 演示脚本抓出的真 bug

`scripts/demo-loop.mjs` 打印真实输出时发现：`loadWeather()` 在 Provider 失败后
回落到 `latestWeatherSnapshot()` 并当作可用数据返回。用户断网后会拿到几分钟前的
天气，却以为拿到了新的。这违反 D-14「不得假装是实时的」。

修复：fetch 失败一律返回 `unavailable`，缓存改由界面层显式调用 `readCachedWeather()`
展示，且必须带 `lastSuccessAt` 让用户知道数据有多旧。

**这个 bug 是靠「把真实输出打印给人看」发现的，任何绿测都测不出来。**

### 浏览器实测抓到的三个 bug（任何绿测都测不出来）

这三个是靠「打开浏览器看真实输出 + 截图核对」发现的，`AGENTS.md` 要求的
「上线 = 部署 + 访客视角首屏核对」不是形式主义：

1. **新植物被误判为「无需处理」**。引擎把「没有浇水记录」和「0 天前浇过」
   当成同一件事（`daysSince ?? 0`），导致首屏显示「今天 0 盆要处理」。
   这与痛点第一条「记不住上次什么时候浇水」直接矛盾。
   修复后：无记录 → CHECK，并明确标注 `source: unknown`（是事实缺失，不是推断）。

2. **来源显示为 `来源：plant-3`**。可追溯性对机器成立，对人不成立。
   新增 `describeSource()` 把 id 翻译成「浇水记录 09-21 14:20 · 实测」，
   并只给真正有原始记录可核对的来源（浇水记录、天气）加「可点开核对」入口，
   推断与未知不给假入口。

3. **5K 屏上行长超过 150 字符**。5K + 100% 缩放下内容拉满宽度，
   正是 AGENTS.md 禁止的「信息密度过高的后台」观感。
   增加 `max-width: 720px / 860px` 限宽。

另外两个布局 bug 也是截图发现的：底栏 fixed 压住主导航、
导航 max-width 约束导致四个按钮文字挤成一团。

### 我自己写错又改对的两个测试

- 「同一次观测的两次抓取必须有不同 id」——**方向就错了**。
  正确语义是 snapshot 的身份是「这份天气数据」，同一次观测重复抓取
  应当是同一条记录并覆盖，否则缓存会堆积重复天气。
- 「无记录时 source 应为 measured」——**前提错了**。
  无记录是事实缺失，必须是 `unknown`，不能伪装成实测。

### 浏览器实测抓到的 bug

**枚举值直接暴露给用户**：详情页显示「客厅 indoor_window」。
这在数据层和界面层都漏了——引擎里有一份中文映射，领域层没有，
于是详情页只能显示英文枚举。
修复：在 `domain/types.ts` 建立 `EXPOSURE_LABEL` 与 `EXPOSURE_DESC` 单一来源，
引擎与界面共用，消除两处口径不一致的可能。

### 我在写统计测试时搞反了一次

构造「间隔变长」的数据时，我按直觉写了 `[w(0), w(2), w(5), w(9), w(15), w(22)]`，
以为间隔在拉长，实际相邻间隔是 `[2,3,4,6,7]`——记录按时间升序后，
`intervals[i]` 对应的是早期到中期的间隔，前半段更长，趋势是**负**的。
先用脚本算出真实数值再改断言，没有靠猜。
